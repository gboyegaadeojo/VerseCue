# Full application review: conversational Scripture operation

2026-11-18 UTC. Reviewed application source at version 0.5.8 and the NR-006 next-verse plan. This is a source review, local synthetic-text investigation and regression checkpoint, not a new live ProPresenter or microphone acceptance test. No runtime behavior was changed.

## Assessment

VerseCue has a working foundation: explicit-reference parsing, local speech workers, bounded background capture, review queue, exact saved-cue dispatch/readback, guarded Auto, stop/recovery, profiles, optional quote matching and an experimental Windows Bible-copy preparation route. Those pieces do not yet provide a complete conversational preaching workflow.

The main missing component is a passage session that connects **what the pastor requested**, **what has been prepared**, **what ProPresenter currently displays**, and **which relative command is allowed next**. These must be separate states with explicit transitions. Adding more phrase aliases alone will not close the gaps below.

## Delivery order

1. **Context and correctness PR:** PW-01 through PW-03. Correct range semantics and intent rejection; implement current-output context verification. Keep relative Auto disabled.
2. **Passage preparation/coverage PR:** PW-04 through PW-06. Make an exact destination's availability and complete coverage explicit, with bounded preparation/reuse and honest platform restrictions.
3. **Speech continuity/reliability PR:** PW-07 through PW-09 and PW-12. Add original-age evidence, stable utterance identity, cross-window stabilization, loss recovery and reproducible ownership diagnostics.
4. **Conversational controls/UX PR:** PW-10, PW-11 and PW-13. Add common anchored commands, edition changes and visible passage-session state with shared manual/voice semantics.
5. **Policy and acceptance PRs:** PW-14 through PW-16. Keep policy changes explicit, collect real evidence and only then consider extending automatic navigation.

Each implementation PR needs failing meaningful regressions first, passing affected unit/integration/UI checks, updated operator documentation and precise acceptance limitations. Preserve original requirements and all current safety, local-only processing and ProPresenter ownership boundaries. These are implementation slices, not five new mandatory user-approval gates.

## End-to-end demonstration required

Start authorized listening with ProPresenter foreground. Pastor says "Hosea one one"; app identifies 1:1, prepares a complete verified passage and offers confirmation. After matching real output readback, "next verse" offers 1:2. "Read verses three through five" offers 1:3-5; the next command offers 1:6. "Same verse in the Amplified version" prepares the same reference in AMP, never KJV. "Don't change it" cancels pending advancement. An operator then selects another passage in ProPresenter; a subsequent relative command is withheld until a new anchor is explicitly established. No unrelated song/media is advanced; uncertain output pauses without retry.

This demonstration must include a split-cue verse, a chapter boundary, an unavailable translation, a slow speech window and an interrupted connection. On unsupported preparation/platform combinations, the expected result is a clear manual-preparation state, not a fabricated success.
